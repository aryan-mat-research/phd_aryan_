Autonomous Line-Following Robot

An Arduino-based four-wheel robot project exploring infrared sensing, motor control, and path-following logic.

Overview

Project question, scope, and system purpose.

Engineering objective

Objective: use IR sensor inputs and Arduino motor commands to guide a robot along a marked path.

The project combines digital I/O, sensor interfacing, motor actuation, and embedded control logic.

System components and functional roles

01

Arduino controller

Runs the embedded sketch, reads digital inputs, and writes output states to control the motors.

02

Infrared sensing

IR sensor inputs are referenced on digital pins 11 and 12 in the uploaded motor-control sketches. The final sensor module and calibration are not identified.

03

Drive motors

Four digital output pins, 7–10, are used as motor-control signals. Comments associate pins 10/9 with the left motor and 8/7 with the right motor.

04

Control software

Separate sketches test motor outputs, serial-command motion, sensor response, and LED blinking as part of the development process.

Contribution and status

Completed undergraduate academic project · Grade A+.

Methods

Hardware logic, pin assignments, and operating sequence.

System implementation

The Arduino C/C++ sketches configure pins in setup() and run control logic in loop(). Serial-control versions use 9600 baud and single-character commands.

Motor-control logic

full_motor_1.ino and day_5_feb.ino assign HIGH/LOW patterns to D7–D10. Actual wheel direction depends on the driver wiring and motor orientation.

Development workflow

  1. Output and LED checksled_blinking.ino toggles D10 with short delays; 2.ino initializes D7–D10 as outputs and repeatedly writes states to D9/D10.
  2. Individual motor experimentsmotar.ino alternates a motor-output pattern and a stop state. fulll_motor.ino defines motion functions and cycles through them, though several functions use identical output patterns in this version.
  3. Combined motor outputsboth_motor.ino initializes D7–D10 and writes output patterns for labelled forward, backward, right, left, and stop phases. In the uploaded version, the four movement phases use the same pattern, so they do not independently demonstrate distinct directions.
  4. Serial-command controlfull_motor_1.ino maps F/B/L/R/S (uppercase or lowercase) to forward, backward, left, right, and halt. day_5_feb.ino maps W/S/A/D/X to similar functions. Serial communication is configured at 9600 baud.
  5. Sensor input experimentssketch_feb04a.ino changes output states based on D12. senser.ino also reads D12, but its logic has a stray semicolon after the first if, so the following block executes unconditionally. These files need correction before being treated as validated sensor-control behaviour.
  6. Integrated line-following controllerA final integration step would continuously read the left and right sensors, interpret the line position, select a motor state, and repeat with suitable timing. A complete verified version of this logic was not present in the supplied sketches.
Code & development

Source files and what each one demonstrates.

Code archive

The sketches document component tests and successive control experiments.

  • full_motor_1.inoSerial control at 9600 baud; F/B/L/R/S commands (case-insensitive); motor outputs on D7–D10; D11 and D12 configured as inputs.
  • day_5_feb.inoSerial control at 9600 baud; W/S/A/D/X commands; similar motor-output functions; sensor pins configured but not used by the command decision logic.
  • both_motor.inoCombined motor-output test with labelled movement stages and a stop stage. Movement stages currently share the same output pattern.
  • motar.inoSimple output test alternating a labelled forward pattern with all four motor-control outputs LOW.
  • fulll_motor.inoDefines forward/backward/left/right/halt functions and runs a timed sequence; several movement functions use identical output states in the supplied version.
  • fulll_motor2.inoAttempted serial-controlled D10 output. The statement char ch=Serial,read(); is malformed and needs correction to Serial.read() before compilation.
  • 2.inoConfigures D7–D10 as outputs and repeatedly writes HIGH to D10 and LOW to D9 with delays.
  • led_blinking.inoIntended LED blinking sequence on D10. The uploaded sketch appears to be missing a closing brace in setup(), so it should be fixed before compilation.
  • sketch_feb04a.inoReads D12 and sets D7–D10 LOW when input is HIGH, or HIGH when input is LOW.
  • senser.inoReads D12 and clears outputs; a stray semicolon after if (digitalRead(12)==0) changes the intended conditional behaviour.

Interpretation

Engineering meaning, limitations, and next steps.

Code interpretation

The code progresses through pin setup, motor-output tests, serial commands, and sensor-input experiments.

Serial commands are manual control, not autonomous navigation.

Limitations visible in the supplied code

  • Some sketches use the same output pattern for multiple named movement functions, so the names do not guarantee distinct physical movements.
  • The sensor test in senser.ino includes a stray semicolon after an if statement, changing the control flow.
  • fulll_motor2.ino contains a malformed serial-read statement, and led_blinking.ino appears to have an unmatched brace.
  • The motor driver, exact sensor hardware, power supply, wiring diagram, and Arduino model are not specified in the uploaded files.
